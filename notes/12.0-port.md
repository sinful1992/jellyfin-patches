release tag, is the repo's source of truth, and `jellyfin-patched:12.0-p1` is built and
smoke-tested. **Not deployed** — see "Before deploying" at the end.

v12.0) and the userdata commit remains unported. The rebase needed no manual conflict
resolution; rerere replayed the MediaInfoHelper resolution banked below.

### The two resolutions

**`MediaInfoHelper.cs`** — purely additive on both sides: rc7 added an
`IServerApplicationHost appHost` field, constructor parameter and doc comment; we add
`IHttpContextAccessor` and `IStreamTicketStore`. Both sides kept. The ticket-issuing
logic itself merged with no conflict at all.

Note for next time: "keep both sides" is right for the fields and the assignments but
**wrong verbatim for the parameter list** — it produced `IServerApplicationHost appHost)`
followed by more parameters, 27 compiler errors. The parameter list needs the sides
joined with a comma.

**`SubtitleEncoder.cs`** — the exact mirror of the resolution taken when this backport
was first cherry-picked onto 10.11.11. There, master's VobSub/MKS lines were context
that did not exist and were dropped; here they are real rc7 code and are kept, and only
our `FindIndex` → `GetSubtitleStreamIndexForFfmpeg` change is applied.

## Why the userdata commit was skipped

Upstream restructured the code the patch targets. At 10.11.11 the defect was
`GetUserData(user, item)` doing `_cache.GetOrAdd(...)` seeded from `item.UserData` — a
stale snapshot became authoritative for every later reader, so a favourite set through
a newer instance was reverted by the next progress report.

At rc7 that method is gone. Reads now go through a new `ResolveUserDataRow(item, ...)`
which picks the row matching the item's current user data keys, and the write paths
rehydrate `item.UserData` from the database after saving.

So the patch cannot be rebased — its target does not exist — and forcing a merge would
produce code shaped for a design upstream has replaced.

**Open question, deliberately not answered here:** whether the original defect still
occurs at rc7. Reads still resolve from the `item.UserData` snapshot, and a pinned stale
instance (`SessionInfo.FullNowPlayingItem`) could still supply stale values to a progress
report that writes every column back — but the shared-cache poisoning that made it
reliable is gone. Answering it needs a running 12.0 to reproduce against, which needs a
base image, which does not exist yet. Do not re-derive the fix blind.

## Tested on the nightly base — it works

Predicted this would fail; it did not. **Measured 2026-09-06:**

    REPO_DIR=<temp> BASE_TAG=v12.0-rc7 build/build.sh   # base = lscr.io/...:nightly

- version gate **passed**: the nightly ships `12.0.0.0` for the three SharedVersion
  assemblies and `26.4.0.0` for `Jellyfin.Api`, matching what an rc7 build emits
- image built, container started, startup wizard completed
- **all three unauthenticated endpoints returned 401** — the patch is live in a 12.0 image

So 12.0 is testable today, despite the nightly being built from `master` (90 commits past
rc7, touching 41 files in the four projects we replace).

**What this does and does not prove.** It proves the assemblies bind and the server boots
with auth enforced. It does not prove the drift is harmless: an rc7-built
`MediaBrowser.Controller` sitting in a master-built graph can still throw
`MissingMethodException` on a path the smoke test never touches — playback, transcoding,
a library scan, the 12.0 Intro Skipper build. Treat it as a testbed, not a daily driver.

One real bug this surfaced: `build.sh` hardcoded `bin/Release/net9.0`, so a 12.0 build
compiled fine and then failed the gate with "no deps.json". The target framework moves
with the base (net9.0 → net10.0); it is now discovered. Shipped in **10.11.11-p4**.

### Three real 12.0 upgrade problems — none caused by our patches

1. **Intro Skipper 1.10.11.23 will not load.** `TypeLoadException: Method
   'CleanupExtractedData' in type 'IntroSkipper.Providers.SegmentProvider' does not have
   an implementation` — it is ABI-locked to 10.11. The 12.0 plugin line exists
   (`12.0/v12.0.2.0`). Not a gate, just swap the build.
2. **`encoding.xml` fails to parse, and hardware acceleration silently reverts to
   `none`.** `Instance validation error: '' is not a valid value for EncoderPreset` —
   the live file has `<EncoderPreset xsi:nil="true" />`, which 10.11 accepted and 12.0
   rejects. The whole encoding config is then discarded: the test instance reported
   `HardwareAccelerationType: none` where live reports `vaapi`. **Fix `EncoderPreset`
   before upgrading**, or every transcode falls back to CPU.
3. **`X-Emby-Token` and `?api_key=` are no longer accepted** — both return `401`; only
   `Authorization: MediaBrowser Token="..."` works. Anything integrating with the server
   by the old forms breaks on upgrade.

Artefacts of the test setup, not defects: artwork `404` (the 3.7 GB metadata directory was
not copied) and two `500`s from deliberately malformed calls of mine — streaming a
`BoxSet` id (`InvalidCastException`) and `GET /Items/{id}` without `userId`
(`ArgumentException: Guid can't be empty`). Both are upstream returning 500 where a 400
belongs.

## What blocks shipping for real

~~**No 12.0 stable, and no lsio image built from a release tag.**~~ **Both cleared
2026-09-08:** upstream cut `v12.0`, and LinuxServer now publishes a release-tag image,
`12.0ubu2604-ls48`, not just `nightly-*`. The 90-commits-of-drift objection is gone, and
so is the lsio → official base-family switch that was being costed as the alternative:
staying on lsio is now possible.

**What still blocks: the repo structure, below.**

`build.sh` also reads `BASE_TAG` and `BASE_IMAGE` from files pinned to 10.11.11, and the
watcher derives expected image names from `VERSION`. A 12.0 build needs those
parameterised per base rather than overwritten — not done, deliberately, because
`patches/` is generated from `patched/10.11.11` and regenerating it from a 12.0 series
would swap out what the live build is made of.

## Resuming

1. Wait for a 12.0 **stable** release and a matching lsio image. **Bloodhound does NOT
   watch base images** — it polls GitHub releases/commits/issues and inspects the local
   image and container, nothing on Docker Hub. The lsio half of this step has to be
   checked by hand, or the watcher grown a base-tag check. Both arrived 2026-09-08:
   upstream `v12.0`, and `lscr.io/linuxserver/jellyfin:12.0ubu2604-ls48`.
2. Re-run `git rebase --onto v12.0 v12.0-rc7 patched/12.0` — rerere replays the
   MediaInfoHelper resolution. **Not `v10.11.11` as the upstream ref**: `patched/12.0` is
   based on rc7, so `v10.11.11..patched/12.0` enumerates 2012 commits, not our five.
3. The BDMV backport **is** in v12.0 — upstream `7c463f5fb` (merged 2026-09-05) is an
   ancestor of the tag, git-confirmed 2026-09-09, and `port-check.py` says DROP. Delete
   the commit rather than resolving it; that also removes the SubtitleEncoder conflict,
   leaving a four-commit branch and one replayed conflict.
4. Decide the userdata question with a reproduction on a running 12.0.

## The userdata question, attempted 2026-09-09 — still OPEN

Reproduced against `jellyfin-patched:12.0-p1` on a copy of the live config (migration
applied cleanly, 1 user, 2787 UserData rows), with **stock `10.11.11ubu2604-ls43` as a
positive control** on its own copy. Both instances driven through a disposable API key
planted in the copy's `ApiKeys` table; the live server was never touched, and both
copies were deleted afterwards.

**Single-instance attempt** — open a session, set the favourite through another path,
fire progress reports: favourite survived on 12.0. **But it also survived on stock
10.11.11**, where the defect is known to exist. The test does not exercise the defect,
so it says nothing about 12.0. (This is the `notes/hls-seek.md` lesson again: a test
that encodes your own premise proves nothing. Run the control first.)

**Two-instance attempt** — two servers on one database, B opens a session and caches the
item, A sets the favourite, B fires progress reports from its stale snapshot:

| | after A sets favourite | after B's progress reports | database |
|---|---|---|---|
| stock 10.11.11 | A=True **B=False** | A=True B=False | `IsFavorite=1` |
| patched 12.0-p1 | A=True **B=False** | A=True B=False | `IsFavorite=1` |

**Identical.** Two things follow:

1. **A second instance serves a stale `IsFavorite` at 12.0 exactly as it does at
   10.11.** B returns `false` while the database says `1`. That is measured, not
   inferred. What is **not** established is the mechanism: this could be the same
   `_cache.GetOrAdd` poisoning, or just ordinary per-process caching that any
   two-instance setup would show. Do not attribute it to the `ResolveUserDataRow`
   restructure without isolating that.
2. **The destructive revert did not reproduce on either version**, so whether it still
   occurs at 12.0 remains **unanswered**. Do not read the table above as "12.0 is fine".

**Lead for the next attempt.** The item carries *three* UserData rows with different
`CustomDataKey`s (`76666000071`, the guid, `tt0088509000071`). The revert may need the
progress write to land on a different key row than the favourite write — which is
exactly the "row matching the item's current user data keys" problem `ResolveUserDataRow`
was introduced to solve. Start there rather than with the session snapshot.

Recreating the test estate is one `rsync -a --exclude=metadata --exclude=cache
--exclude=transcodes --exclude=log` of `/mnt/data/docker-data/jellyfin/` plus a planted
`ApiKeys` row.
